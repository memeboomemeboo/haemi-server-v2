## 1. 결론

인가 단위는 가족이 아니라 보호자와 어르신 사이의 `GuardianElderLink`다. 가족에 보호자나 어르신이 추가되면 링크가 자동 생성되므로, 같은 가족 보호자는 각자 연결된 어르신의 추억과 답변을 함께 조회한다. 추억 수정·삭제와 관계 라벨 변경은 작성자 또는 링크 소유자 본인만 가능하고, 하루 한마디는 예외적으로 사적이다.

보호자 본인 프로필과 MVP 가족 탈퇴 제외는 현재 동작과 일치한다. 초대 코드, 가족 단건 조회, 발신 하루 한마디 이력, 출석·리포트 조회는 구현됐다. 리포트는 `AttendanceRecorded`와 `CognitiveTrainingCompleted` 스냅샷만 소비하며, RPT-ATT-004~006도 보호자 전용 API로 제공한다. 어르신 프로필 수정 API·다중 사용자 HTTP 인수 테스트의 부족 여부는 아래 초기 검토 이후 별도 재검증이 필요한 항목이다.

첨부 대화의 “AI한테 넣고 돌리셈”은 분석 수행 지시로 보며 제품 기능 요구사항으로 확정하지 않았다. 기존 명세도 `platform/ai`를 하이라이트 자동 생성의 후보로만 적고 있다. 상태 색과 점수 계산은 AI 적용 여부와 무관하게 재현 가능한 규칙으로 산출해야 한다.

## 3. 확정 정책

1. 어르신은 본인에게 전달된 추억만 조회하고, 보호자는 연결된 어르신의 추억을 작성자와 무관하게 모두 조회한다.
2. 하루 한마디는 발신 보호자와 수신 어르신만 조회한다. 다른 보호자에게는 존재 자체를 노출하지 않는다.
3. 어르신 프로필은 링크된 모든 보호자가 수정한다. 가족 대표자 기반 권한 강화는 MVP 이후다.
4. 가족 생성 시 초대 코드를 발급하고 다른 보호자만 합류한다. 어르신은 초대 대상이 아니다.
5. 어르신 리포트는 보호자만 조회한다.
6. 보호자 프로필은 로그인한 본인만 조회한다.
7. 활동 참여 빈도는 최근 7일의 요일별 완료 점(●/○)과 최근 4주 막대로 표시한다.
8. 보호자의 가족 탈퇴 경로는 MVP 이후 제공한다.
9. 보호자는 한 가족에만 속하므로 가족 목록과 상세 API를 나누지 않는다. 단일 응답을 프론트가 화면별로 나눠 사용한다.

## 4. 관계 라벨 표시

### 현재 동작

`GuardianElderLink`가 보호자·어르신 조합마다 관계를 저장하므로 같은 어르신을 A 보호자는 `딸`, B 보호자는 `손녀`로 저장하고 조회할 수 있다. 홈은 `roleOf(guardianId, elderId)`를 사용하고, 프로필은 본인의 링크 role을 사용한다. 다른 보호자의 role은 바꿀 수 없다.

### 방향별 계약이 필요한 부분

| 보는 방향 | 현재 상태 | 권장 표시 |
| --- | --- | --- |
| 보호자 → 어르신 | 구현됨 | 내 링크의 관계를 그대로 표시 |
| 어르신 → 보호자 | 추억 생성자의 role을 그대로 반환하며 null 가능 | `딸 김OO님`; `보호자`·`기타`·null은 관계를 생략하고 이름만 표시 |
| 보호자 → 다른 보호자 | 조회 경로 없음 | 현재 선택한 어르신을 기준으로 `박OO 어르신의 손녀 · 김OO`처럼 표시 |

가족에 어르신이 여러 명이면 한 보호자가 어르신마다 다른 관계를 가질 수 있다. 따라서 가족 단건 응답의 `guardians[].role` 단일 필드는 정보가 손실된다. 다음처럼 어르신별 관계를 내려주는 구조가 안전하다.

```json
{
  "familyId": "...",
  "guardians": [
    {
      "guardianId": "...",
      "name": "김OO",
      "isMe": false,
      "relations": [
        { "elderId": "...", "role": "손녀" },
        { "elderId": "...", "role": "보호자" }
      ]
    }
  ],
  "elders": [
    { "elderId": "...", "name": "박OO", "birthDate": "1948-03-01", "myRole": "딸" }
  ]
}
```

이는 다른 보호자의 프로필 공개가 아니다. 가족 화면에 필요한 `guardianId`, 표시 이름, 어르신별 관계만 제공하고 전화번호·로그인 ID·생년월일은 제외한다.

## 5. 컨디션 카드 데이터 갭

첨부 시안의 요소를 현재 API와 대조한 결과다.

| 화면 요소 | 현재 제공 여부 | 판단 |
| --- | --- | --- |
| 어르신 선택 | 가능 | 보호자 홈 응답의 연결 어르신 목록 사용 가능 |
| “오늘 컨디션 좋아요” | 불가 | 상태 산출 데이터와 리포트 모듈 없음 |
| 점수 링 `82` | 불가·명세 충돌 | 기능명세는 내부 점수 미노출과 3색 라벨만 허용 (`RPT-ATT-004`) |
| 인지 활동 2회 | 부분 가능 | 10문항 세션·완료 기록·출석 원천은 존재 | 보호자용 주간 활동 횟수 집계·표시 API는 없음 |
| 마지막 접속 1시간 전 | 불가 | 계정에 최종 접속 시각 필드 없음 |
| 최근 7일 완료 점·최근 4주 막대 | 부분 가능 | 출석 데이터는 `DailyParticipation`에 적재됨 | `guardian/report` 집계·조회 API가 아직 없음 |

현재 프론트는 오늘 출석·스트릭·D+·배지만 실제 데이터로 표시할 수 있다. 종합 컨디션, 점수 링, 활동 횟수, 마지막 접속, 최근 7일·4주 집계는 리포트 구현 전까지 숨김 또는 명시적인 준비 중 상태여야 한다. 점수 링은 3색 상태 라벨과 주간 참여 집계로 대체한다.

## 6. 추가 결정·구현 필요 사항

이미 확정된 “단일 가족 API”, “가족 탈퇴 MVP 이후”, “최근 7일 완료 점 + 최근 4주 막대 표시”를 다시 결정 항목으로 올리지 않았다. 아래는 그 결정을 구현하기 위해 새로 확정해야 하거나 코드에서 추가로 확인된 항목이다.

| 우선순위 | 항목 | 필요한 결정 또는 조치 |
| --- | --- | --- |
| 상 | 초대 코드 안전성 | 충분한 엔트로피, 만료·재발급·폐기, 오입력 rate limit, 사용 전 가족명 확인, 합류 성공 시 원자적 처리 |
| 상 | 한 가족 제약의 동시성 | 현재 조회 후 추가 방식은 두 가족에 동시에 합류할 수 있다. 계정 또는 멤버십 기준 잠금 등으로 R2를 원자적으로 보장 |
| 상 | 되돌릴 수 없는 잘못된 합류 | MVP에는 탈퇴가 없으므로 합류 전 가족명·접근 범위를 확인시키고 운영자 교정 절차 마련 |
| 상 | 가족 단건 응답 | 미소속 응답 형식, 다른 보호자의 최소 공개 필드, 다중 어르신 관계 배열 형식 확정 |
| 상 | 추억 생성자 분기 | 보호자용 추억 목록·상세 응답에 생성자 정보 또는 `isMine`이 없어 수정·삭제 버튼을 안전하게 분기할 수 없음 |
| 상 | 어르신 프로필 공동 수정 | 수정 가능 필드, 마지막 수정자·시각, 동시 수정 충돌 처리와 변경 이력 필요 |
| 상 | 휴대폰 인증·로그인 시도 제한 | 인증번호 확인·재발송과 로그인 실패에 횟수 제한이나 잠금이 없음 |
| 중 | 하루 한마디 발신 이력 | 발신자 본인 조회 API와 보관 기간·삭제 시점 안내 필요 |
| 중 | 관계 라벨 | 배우자·며느리·사위 등 목록, `기타` 입력·표시, 코드값과 한글 표시명 분리 여부 확정 |
| 중 | 관계 수정 경로 | 링크 단건 PATCH와 프로필 일괄 PATCH가 공존하고 실패 코드가 다르므로 하나로 통합 |
| 중 | 추억 생성자 fallback | 링크 해제 후 `creatorRole`이 null이 될 수 있으므로 이름·관계 누락 시 표시 규칙 필요 |
| 중 | 어르신 답변 오조작 | 같은 추억에 답변을 반복 생성할 수 있고 수정·취소 API가 없어 중복 탭 처리 정책 필요 |
| 중 | 추억 등록량 | 일·주 단위 상한이나 정렬·페이징 정책이 없어 다수 보호자가 등록할 때 앨범 과밀 가능 |

## 7. 테스트·API 확인

- 통과: `CareAccessQueryTest`, `JoinFamilyUseCaseTest`, `ElderMemoryQueryImplTest`, `RegisterMemoryUseCaseTest`, `SendDailyCareUseCaseTest`, `CreateResponseUseCaseTest`, `ApplicationStartupHttpTest`
- `ApplicationStartupHttpTest`에서 실제 Spring 서버가 기동됐고 health 200, 보호자 API 무토큰 요청 401, 입력 오류 400과 애플리케이션 종료 로그를 확인했다.
- 인증된 보호자 두 명과 어르신 계정을 구성하는 E2E fixture가 없어 동일 가족 간 실제 HTTP 응답은 호출하지 못했다. 구현 판정은 컨트롤러→유스케이스→저장소 코드와 단위 테스트를 함께 근거로 삼았다.

## 8. 권장 구현 순서

1. 초대 코드와 한 가족 동시성 보장, 합류 확인 화면용 가족 미리보기
2. 가족 단일 조회 API와 다중 어르신 관계 응답 계약
3. 보호자용 추억 응답의 `isMine`·생성자 정보
