# 해미 v2 — 인가 규칙 (확정)

> 기준: [v2-funcctional-spec.md](./v2-funcctional-spec.md) · [v2-module-architecture.md](./v2-module-architecture.md)
> 확정일: 2026-08-24
> 소유 모듈: `guardian/eldermanagement/access`
> 구현 검증: [v2-guardian-permission-review.md](./v2-guardian-permission-review.md)

v1이 `elders.group_id UNIQUE`로 우회했던 지점입니다. **이 문서가 인가에 관한 유일한 근거**이며, 여기에 없는 판단은 구현하지 말고 확인을 받습니다.

---

## 1. 모델

```
User (auth/account)
 ├─ role = GUARDIAN
 └─ role = ELDER ──── Elder (guardian/eldermanagement)  1:1

Family ──< FamilyMember >── User(GUARDIAN)      최대 8명
   │
   └──< Elder                                   최대 4명

GuardianElderLink                               ★ 인가의 단위
 ├─ guardianId (User)
 ├─ elderId (Elder)
 ├─ role (보호자/딸/아들/손녀/손자/기타)
 └─ linkedAt
```

**인가 판정의 단위는 가족이 아니라 `GuardianElderLink`입니다.**

근거: 명세 MYP 프로필 수정 — *"등록한 어르신**마다** 어르신에 대한 보호자의 역할을 선택할 수 있다"*. 관계가 어르신 단위로 존재하므로 권한도 어르신 단위입니다. 가족 단위로 판정하면 이 역할 라벨이 걸 자리가 없어집니다.

---

## 2. 확정 규칙

### R1. 인원 상한

| 대상 | 상한 | 근거 |
| --- | --- | --- |
| 가족당 어르신 | **4명** | 명세 MYP 가족 생성에 명시 |
| 가족당 보호자 | **8명** | 어르신 4명 기준 자녀·손주 수용. 명세에 없어 새로 정함 |

상한은 **DB 제약이 아니라 애플리케이션 검증**으로 둡니다. 설정값(`haemi.family.max-elders=4`, `max-guardians=8`)으로 노출합니다.

> **v1의 실패를 반복하지 않기 위한 원칙**: 카디널리티를 DB `UNIQUE`로 굳히지 않습니다. v1은 `uk_elders_group UNIQUE(group_id)`로 1:1을 박아 넣어 4명 확장이 불가능해졌습니다. 스키마는 다대다로 두고 제한은 코드에서 겁니다.

### R2. 소속

| 규칙 | 값 | 근거 |
| --- | --- | --- |
| 보호자가 속할 수 있는 가족 수 | **1개** | 명세 MYP 프로필 조회 *"(가족) 속한 가족을 조회"* — 단수 |
| 어르신이 속할 수 있는 가족 수 | **1개** | 동일 |

**스키마는 다대다(`family_members` 조인 테이블)로 두고, 애플리케이션에서 1개로 제한합니다.** 나중에 다가족을 허용해도 마이그레이션이 필요 없습니다.

### R3. 링크 생성

**가족에 어르신이 추가되면, 그 가족의 모든 보호자에 대해 `GuardianElderLink`가 자동 생성됩니다.** 보호자가 가족에 합류할 때도 같습니다(그 가족의 모든 어르신에 대해 생성).

- 가족 생성 시 초대 코드를 발급하고, 기존 가족 합류는 `familyId` 직접 입력이 아니라 초대 코드 검증을 거칩니다.
- 초대 대상은 `GUARDIAN`만 허용합니다. 어르신 계정은 가족 초대 대상이 아닙니다.
- 기본 역할은 `보호자`. 각자 MYP에서 자기 역할을 바꿉니다.
- 링크는 개별 행이므로 **나중에 선택적 해제가 가능**합니다(MVP에서는 UI 미제공).

근거: UX는 "가족이면 다 본다"로 단순하게, 모델은 어르신 단위로 유연하게 가져갑니다.

### R4. 시점 — 과거 데이터 접근

**나중에 합류한 보호자도 그 이전의 어르신 답변·리포트를 전부 봅니다.**
**추억은 최근 1년 이내로 조회됩니다 (D21).** 1년보다 오래된 추억은 보호자·어르신 화면 모두에서 제외되며, 페이징은 아직 없습니다.

근거: 가족 앨범의 성격상 "합류 전 추억은 안 보입니다"는 부자연스럽지만, 데이터 누적에 따른 성능·UX를 고려해 추억 조회에는 최근 1년 창을 둡니다(D21). 어르신 답변·리포트는 상태 파악이 목적이라 과거 추세가 필요해 전체 기간을 유지합니다.

**예외: 하루 한마디(R6).**

### R5. 추억 (`guardian/memory`, `elder/response`)

| 행위 | 권한 |
| --- | --- |
| 추억 등록 | 대상 어르신에 링크된 보호자 |
| 추억 조회 | 대상 어르신에 링크된 **모든** 보호자 + 대상 어르신 본인 |
| 추억 수정·삭제 | **생성자 본인만** (`created_by`) |
| 어르신 답변 조회 | 대상 어르신에 링크된 **모든** 보호자 |
| 어르신 답변 작성 | 대상 어르신 **본인만** |

근거: 명세 E-ALB 조회에 *"추억 생성자(관계, 이름)"* 를 어르신에게 표시한다고 되어 있습니다. 여러 보호자가 올린다는 전제이므로 조회는 공유, 수정은 생성자 한정입니다.

### R6. 하루 한마디 (`guardian/dailycare`, `elder/inbox`) — 유일한 사적 리소스

| 행위 | 권한 |
| --- | --- |
| 전송 | 대상 어르신에 링크된 보호자 |
| 조회 | **발신 보호자 본인 + 수신 어르신만** |

**다른 보호자에게는 보이지 않습니다.** 음성 1분·텍스트 100자의 1:1 사적 메시지이고, 가족 전체에 공개되면 사용하지 않게 됩니다.

전송 상한은 **`(보호자, 어르신, 날짜)` 조합당 1회**입니다. 명세: *"가족에 등록된 어르신의 수 만큼 하루 한 마디 전할 수 있음"*.

### R7. 리포트 (`guardian/report`)

| 행위 | 권한 |
| --- | --- |
| 어르신 목록·리포트 조회 | 링크된 보호자 |
| 어르신 간 비교·순위 | **금지 — 기능 자체를 만들지 않음** |

`RPT-LST-001`의 목록은 "각자 본인 기준선 대비" 상태만 표시합니다. `accessibleElders(guardianId)`가 반환한 어르신만 목록에 들어갑니다.

### R8. 어르신 계정 관리

| 행위 | 권한 |
| --- | --- |
| 어르신 계정 생성 | 가족에 속한 보호자 (R1 상한 검증) |
| 어르신 프로필 수정 | 링크된 **모든** 보호자 |
| 보호자–어르신 링크 해제 | 링크된 보호자 본인 |
| **마지막 링크 해제** | **금지** — 최소 1명의 보호자가 남아야 함 |
| 어르신 계정 삭제 | 링크된 보호자 (§6 데이터 처리 미확정) |

마지막 링크 해제를 막는 이유: 아무 보호자도 없는 어르신 계정은 로그인은 되는데 아무도 관리할 수 없는 고아 상태가 됩니다.

### R9. 어르신 권한

**어르신은 자기 리소스만 접근합니다.** 다른 어르신의 리소스에 접근하는 API 경로를 **아예 만들지 않습니다.**

| 행위 | 권한 |
| --- | --- |
| 받은 추억 조회·답변 | 본인 수신분만 |
| 하루 한마디 수신 | 본인 수신분만 |
| 인지 훈련 | 본인 세션만 |
| 자기 리포트 조회 | **불가** — 점수·정답률은 어르신에게 노출 금지 |

마지막 항목이 중요합니다. 명세: *"진단명·등수·타 어르신 비교 절대 미노출"*, *"오답 페널티 없음"*.

### R10. MVP 제외

| 항목 | 사유 |
| --- | --- |
| 어르신이 보호자를 차단·해제 | 명세에 없음. 어르신 UX 단순화 |
| 보호자의 가족 탈퇴 경로 | MVP 이후 제공 |
| 가족 소유권 이전 | 명세에 없음 |
| 가족 대표자·보호자 등급 구분 | MVP에서는 모든 보호자가 동등. 대표자 기반 권한 강화는 MVP 이후 제공 |

### R11. 보호자 프로필

보호자 프로필 조회·수정은 **로그인한 본인만** 가능합니다. 요청 경로에서 임의의 보호자 ID를 받지 않고 인증 주체의 ID를 사용합니다.

가족 단건 조회에서 다른 보호자의 최소 식별 정보와 어르신별 관계를 보여주는 것은 프로필 조회가 아니라 **가족 구성원 확인**입니다. 이 응답에는 전화번호·로그인 ID·생년월일 같은 프로필 개인정보를 포함하지 않습니다.

## 3. 인터페이스

```java
// guardian/api/CareAccessQuery.java  — 그룹 간 유일한 인가 통로
public interface CareAccessQuery {

    /** 링크가 없으면 CareAccessDeniedException. elderId를 다루는 모든 유스케이스의 첫 줄. */
    void requireGuardianOf(UserId guardianId, ElderId elderId);

    /** 어르신 본인 확인. 어르신 유스케이스의 첫 줄. */
    void requireSelf(UserId actorId, ElderId elderId);

    boolean canAccess(UserId guardianId, ElderId elderId);

    /** 목록 조회용. 반환된 것 외에는 노출 금지. */
    List<ElderId> accessibleElders(UserId guardianId);

    /** 역할 라벨 (딸/아들/손녀 …). 리포트 카드 표시용. */
    GuardianRole roleOf(UserId guardianId, ElderId elderId);
}
```

**소유자 검증(`created_by`)은 이 인터페이스에 넣지 않습니다.** 추억 수정 권한처럼 리소스 내부 사정은 해당 모듈이 판단합니다. 인가 관문은 "이 어르신에 접근 가능한가"까지만 답합니다.

## 4. 실패 응답

| 상황 | HTTP | 코드 |
| --- | --- | --- |
| 토큰 없음·만료 | 401 | `UNAUTHENTICATED` |
| 역할 불일치 (어르신이 보호자 API 호출) | 403 | `ROLE_NOT_ALLOWED` |
| 링크 없음 | 403 | `CARE_ACCESS_DENIED` |
| 생성자 아님 (추억 수정) | 403 | `NOT_RESOURCE_OWNER` |
| 상한 초과 | 409 | `FAMILY_CAPACITY_EXCEEDED` |
| 마지막 보호자 해제 시도 | 409 | `LAST_GUARDIAN_CANNOT_LEAVE` |

**404가 아니라 403으로 통일합니다.** 가족 서비스라 리소스 존재를 추측하는 공격의 실익이 낮고, 403이 디버깅에 유리합니다.

인가 실패는 **전부 로깅**합니다(`guardianId`, `elderId`, 리소스, 시각). 어르신 개인정보는 로깅하지 않습니다.

## 5. 강제 장치

### ArchUnit (CI 게이트, 실패 시 머지 불가)

| # | 규칙 |
| --- | --- |
| AU-1 | `**/application/**`의 public 메서드 중 파라미터에 `ElderId`를 받는 것은 `CareAccessQuery`의 `requireGuardianOf` 또는 `requireSelf` 호출을 포함해야 한다 |
| AU-2 | `elder/presentation/dto/**`의 필드명에 `score`, `correct`, `rate`, `accuracy`, `rank`, `level` 사용 금지 |
| AU-3 | `elder/**`는 `guardian/**` 중 `guardian.api` 외 패키지를 import할 수 없다 |

### 테스트 (유스케이스마다 필수 1건)

```java
@Test
void 링크없는_보호자는_403() {
    // 다른 가족의 보호자로 호출 → CareAccessDeniedException
}
```

**인가 테스트가 없는 유스케이스 PR은 반려합니다.**

## 6. 미확정 — 구현 중 만나면 멈추고 확인

| 항목 | 왜 지금 못 정하나 |
| --- | --- |
| **어르신 계정 삭제 시 데이터 처리** | 추억·훈련 기록·답변을 지울지 익명화할지. 다른 보호자의 추억도 함께 사라지는 문제 |
| **가족 해체** | 어르신 0명 + 보호자 1명일 때만 허용할지, 아예 막을지 |
| **어르신 전화번호 중복** | 한 어르신을 두 가족이 각각 등록하는 경우 (재혼 가정 등) |
| **초대 코드 수명주기** | 만료 시간·재발급·폐기·오입력 시도 제한·동시 합류 처리 규칙 필요 |
