## 0. 요약

인가 판정 단위는 가족이 아니라 **`GuardianElderLink`(보호자–어르신 개별 링크)** 다.
같은 가족 보호자끼리는 R3에 따라 링크가 자동 생성되므로 기본은 "가족이면 다 본다"이고, 원칙은 셋이다.

> **읽기는 전면 공유 · 쓰기는 본인 것만 · 하루 한마디만 완전 사적**

보호자 등급(관리자/일반)은 **없다**. 모든 보호자가 동등하다 (R10, MVP 제외 확정).
MVP 이후 *가족 대표자* 설정으로 권한을 강화할 예정이다.

### 가족 조회 API 현황 — ✅ 세부 조회 구현됨 ([#22](https://github.com/memeboomemeboo/haemi-server-v2/issues/22))

`FamilyController`는 이제 `GET /api/v1/guardian/families/my`로 가족 세부(구성원 포함)를 내려준다.
아래 §D10 절의 "신설할 것은 단일 조회 엔드포인트 하나다" 제안이 그대로 구현된 상태다.

| 메서드 | 경로 | 용도 |
| --- | --- | --- |
| `POST` | `/api/v1/guardian/families` | 가족 생성 |
| `POST` | `/api/v1/guardian/families/join` | 초대 코드로 가족 합류 |
| `GET` | `/api/v1/guardian/families/my` | 가족 세부 조회 (구성원·어르신 목록 포함) |

가족 정보는 여전히 **보호자 프로필 응답에도** 요약이 끼워져 내려간다 (`ProfileController.java:44`).

```
GET /api/v1/guardian/profile
  → family : { familyId, name, memo, profileImageUrl }
  → elders : [ { elderId, name, birthDate, role } ]   // 내 링크 기준 role
```

**API를 나누지 않는 것으로 확정했다 (D10).** R2에서 "보호자는 1개 가족에만 속함"이 확정됐고
`GetGuardianProfileUseCase`도 `findByMembers_UserId`로 `Optional<Family>` 단수를 반환한다.
**사용자당 가족이 항상 1개이므로 "목록"이라는 개념 자체가 성립하지 않는다.**

**화면 분할은 프론트가 담당한다.** 백엔드는 단일 응답으로 전부 내려주고,
프론트가 필요에 따라 요약 영역·구성원 목록·어르신 목록으로 나눠 렌더링한다.
서버 왕복이 1회로 끝나므로 화면 전환 시 로딩이 없다는 이점도 있다.

**신설할 것은 단일 조회 엔드포인트 하나다.** 현재 프로필에 끼워 내려가는 가족 정보에는
**구성원(다른 보호자) 목록이 없어** A2(초대 코드로 누가 합류했는지 확인 불가)가 발생한다.
이 API가 곧 A2의 해결책이다.

```
GET /api/v1/guardian/families/my
  → { familyId, name, memo, profileImageUrl, inviteCode,
      guardians : [ { userId, name, role, isMe } ],   // role = 어르신 기준 관계 (Q8-1-(3))
      elders    : [ { elderId, name, birthDate, myRole } ] }
```

- 소속 가족이 없으면 404가 아니라 **`family: null`** 로 응답한다 (가족 생성 유도 화면 분기용)
- `guardians[].role`은 어르신이 2명 이상일 때 **현재 선택된 어르신 기준** 하나만 내려준다 (Q8-1-(3))
- `inviteCode`는 D4 구현 시 함께 포함한다
- 프로필 응답의 `family` 필드는 **중복이므로 유지 여부를 함께 결정**해야 한다 (§6 액션 2)
- 이 응답 하나로 프론트의 **가족 요약·구성원 목록·어르신 목록 화면을 모두 그린다.** 추가 호출 없음

### 역할 분리 (보호자 API vs 어르신 API)

`SecurityConfig.java:25-26`에서 경로 단위로 강제된다. 역할 불일치는 403 `ROLE_NOT_ALLOWED`.

```
/api/v1/guardian/**  → hasRole("GUARDIAN")
/api/v1/elder/**     → hasRole("ELDER")
```

## 3. 질의 응답 — 코드 확인 결과

### Q5. 홈 "어르신 컨디션" 지표가 API에 있는가 → **없다**

보호자 홈이 내려주는 필드는 4개뿐이다 (`GetGuardianHomeUseCase.java`).

| 필드 | 의미 | 실제 상태 |
| --- | --- | --- |
| `daysTogether` | 함께한 일 수 | ⚠️ **항상 0** — 스텁 |
| `attendedToday` | 오늘 출석 | ⚠️ **항상 false** — 스텁 |
| `greetingSentToday` | 내가 오늘 한마디 보냈는지 | ✅ 실제 값 |
| `challenge` | 도전과제 2종 완료 여부 | ✅ 실제 값 |

**컨디션(🟢좋음 / 🟡보통 / 🟠관찰필요)을 산출할 재료가 API에 하나도 없다.**

- `AttendanceQuery` 구현체는 `AttendanceQueryStub` 하나뿐이고 `completedToday=false`, `currentStreak=0`, `daysTogether=0`을 고정 반환한다.
- `guardian/report` 패키지는 **디렉터리만 있고 자바 파일이 0개**다.
- 산출 규칙 자체는 명세에 수치로 확정돼 있다 — 출석(RPT-ATT-003: 주 5일↑🟢 / 3~4일🟡 / 2일↓🟠), 인지 영역(RPT-ATT-004: 최근 7일 정답률 70% / 40% 구간).

→ 홈 컨디션 표시는 **`elder/attendance` 실구현 + `guardian/report` 착수 없이는 불가능**하다.
프론트는 그때까지 컨디션 섹션을 **숨기거나 스켈레톤 처리**해야 한다.

### Q5-1. 컨디션 카드 목업 대비 데이터 갭

2026-08-24 공유된 홈 컨디션 카드 시안(점수 링 + 요일별 막대 + 활동 요약)을 기준으로 대조한 결과.

| 화면 요소 | 필요한 데이터 | 현황 |
| --- | --- | --- |
| 어르신 선택 드롭다운 | `accessibleElders(guardianId)` | ✅ **유일하게 지금 가능** |
| "오늘 컨디션 좋아요" 문구 | 종합상태 산출 | ❌ `guardian/report` **자바 파일 0개** |
| **점수 링 (82)** | 0~100 수치 점수 | ❌ 없음 + ⚠️ **명세 위반 소지** (아래 C1) |
| "인지 활동 2회" | 훈련 세션 카운트 | ❌ `elder/training`에 **enum 2개뿐**(`SessionStatus`, `QuestionType`). 세션 엔티티·리포지토리 없음 |
| "마지막 접속 1시간 전" | 최종 접속 시각 | ❌ **필드 자체가 없음** — `lastLoginAt` 류 컬럼 코드베이스 전체 0건 |
| 요일별 막대 7개 | 일별 참여 강도 | ❌ `elder/attendance` **자바 파일 0개** + D7과 충돌 (아래 C2) |

#### C1. 수치 점수 노출은 명세와 충돌한다 — 🔴

명세 RPT-ATT-004가 명시적으로 금지한다.

> 내부 점수 미노출, 본인 기준선 대비 추세 + **3색 라벨로만** 번역
> 진단명·등수·타 어르신 비교 **절대 미노출**

이 제약은 어르신 화면만이 아니라 **보호자 리포트에 걸린 규칙**이다. 82점이 보호자에게 나가면

1. 형제자매·친척 간 어르신 점수 비교가 시작된다 (R7이 금지한 "어르신 간 비교"가 UI로 부활)
2. 점수 하락이 곧 진단으로 읽힌다
3. 어르신이 보호자 폰을 넘겨다볼 때 그대로 노출된다

명세가 3색 라벨을 고수한 이유가 이것이다. **점수 링을 쓰려면 명세 개정이 선행되어야 한다.**

#### C2. 요일별 막대는 D7을 뒤집는다 — 🟡

D7은 "주별·월별만, 일별 그래프 없음"으로 확정됐으나 이 카드는 일별이다.
다만 명세 RPT-ATT-003("요일별 완료 점 ●○")과는 **맞는다.** → A14 결정이 선행되어야 한다.

추가로 막대 **높이가 제각각**인 점이 문제다. 명세의 요일별 표시는 완료/미완료 **이진값(●○)** 이다.
높이 차이를 주려면 "그날의 점수"가 필요한데 그것이 C1에 걸린다.

#### 명세를 지키면서 레이아웃을 살리는 안

골격은 유지하고 두 군데만 바꾼다.

| 원안 | 대안 | 근거 |

### Q6. AI 적용 범위

명세가 이미 AI 후보로 지목한 지점은 **RPT-ATT-005(이번 주 하이라이트)** 이고,
모듈 표에도 `platform/ai — 명세 없음 (RPT-ATT-005 자동 생성 후보)`로 적혀 있다.
홈 컨디션 **문구**도 같은 파이프라인으로 묶는 것이 자연스럽다.

**단, 배지 색(🟢🟡🟠) 자체는 AI가 정하면 안 된다.**
색은 규칙 엔진이 계산하고, AI는 그 결과를 **문장으로 번역**하는 역할만 맡는 구조를 권한다.

> 이유: ① 같은 데이터에 다른 색이 나오면 보호자 신뢰를 잃는다 ② "진단명·등수 절대 미노출" 제약을 자유 생성 모델로 보장하기 어렵다 ③ 명세에 이미 수치 기준이 확정돼 있어 AI에 맡길 판단 여지가 없다.

### Q8. 가족 호칭 지침 → **enum 6개가 전부. 지침은 없다**

```java
public enum GuardianRole { 보호자, 딸, 아들, 손녀, 손자, 기타 }
```

| 문제 | 내용 |
| --- | --- |
| 커버리지 부족 | **배우자·사위·며느리·조카·형제자매**가 없어 전부 `기타`로 뭉개진다. 특히 어르신의 배우자는 보호자 8명 상한을 쓰는 시나리오에서 반드시 등장한다 |
| 한글 enum 상수 | JSON에 한글 문자열이 그대로 나간다. 프론트가 이 값을 키로 쓰면 표시명 변경 시 API 호환이 깨진다 → `DAUGHTER("딸")` 형태로 **코드값 + 표시명 분리** 필요 |
| 방향이 한쪽뿐 | 보호자→어르신 호칭만 있고, **어르신 화면에서 보호자를 부르는 규칙**이 없다. `MemoryDetail.creatorRole`이 어르신에게 그대로 노출되는데 `기타`가 오면 "기타 ○○○님이 보낸 추억"처럼 문장이 깨진다 |

**결정 필요**: 호칭 목록 확정 + `기타` 선택 시 표시 문구.

### Q8-1. 관계 라벨이 **어느 관계에서 어떻게 보이는가** — 표시 설계

라벨은 `GuardianElderLink(guardianId, elderId, role)` 한 곳에만 저장되지만,
**보는 사람에 따라 의미가 달라진다.** 방향별로 규칙을 따로 정해야 한다.

#### (1) 보호자 → 어르신 — ✅ 구현됨

내 링크의 `role`을 그대로 표시한다. 항상 **1인칭 기준**이다.

| 화면 | 표시 예 | 구현 |
| --- | --- | --- |
| 보호자 홈 어르신 카드 | `황정빈 어르신 · 78세 · 딸` | `GetGuardianHomeUseCase.java:41` |
| 마이페이지 어르신 목록 | `황정빈 — 딸` | `GetGuardianProfileUseCase` |
| 리포트 목록 카드 | `이름 · 관계 라벨 · 연세 · 출석 · 상태` | 명세 RPT-LST-001 / 미구현 |

같은 어르신을 A는 "딸", B는 "손녀"로 본다. ✅ 정상 동작.

#### (2) 어르신 → 보호자 — ⚠️ 노출은 되는데 규칙이 없다

어르신 화면에서 추억 생성자를 표시할 때 `creatorRole`이 **그대로 나간다**
(`MemoryDetail.java`, `MemorySummary.java`). 명세 E-ALB의 "추억 생성자(관계, 이름)" 요구사항이다.

문제는 **방향이 뒤집혔는데 값은 그대로**라는 점이다.

| 저장된 값 | 어르신 화면 문장 | 자연스러운가 |
| --- | --- | --- |
| `딸` | "딸 황정빈님이 보낸 추억" | ✅ |
| `손녀` | "손녀 황정빈님이 보낸 추억" | ✅ |
| `보호자` (기본값) | "보호자 황정빈님이 보낸 추억" | ⚠️ 어색 — 아무도 안 바꾸면 이게 기본 |
| `기타` | "기타 황정빈님이 보낸 추억" | ❌ 문장이 깨진다 |

**확정 필요 규칙**

- `기타`·`보호자`일 때는 **관계를 생략하고 이름만** 표시한다 (예: "황정빈님이 보낸 추억")
- 어르신은 라벨을 **바꿀 수 없다** (읽기 전용). 어르신이 보호자를 차단·수정하는 기능은 R10에서 MVP 제외
- 어르신 화면은 큰 글씨·단순 문장이 원칙이므로, 관계는 **이름 앞 수식어 한 단어**로만 쓴다

#### (3) 보호자 → 다른 보호자 — ❌ **현재 표시 경로 자체가 없다**

D6(보호자 프로필은 본인만 조회)으로 인해, 지금은 **다른 보호자의 이름도 관계도 볼 수 없다.**
추억 목록에서 남이 올린 추억을 봐도 누가 올렸는지 알 수 없다(A3).

여기서 설계상 가장 까다로운 지점이 나온다.

> **다른 보호자의 라벨은 그 사람이 "어르신에 대해" 가진 관계이지, "나에 대해" 가진 관계가 아니다.**

즉 B의 라벨이 "손녀"라고 해서 B가 **나의** 손녀인 것이 아니다. 어르신 기준의 관계다.
따라서 보호자끼리 볼 때는 **반드시 어르신을 기준점으로 명시**해야 오해가 없다.

| 방식 | 표시 예 | 평가 |
| --- | --- | --- |
| 라벨만 | `손녀 김OO` | ❌ "내 손녀"로 오해 |
| **어르신 기준 명시** | `황정빈 어르신의 손녀 · 김OO` | ✅ 권장 |
| 이름만 | `김OO` | 안전하지만 정보량 없음 |

**확정 필요 규칙**

- 보호자끼리 보이는 화면에서는 라벨을 **"{어르신 이름} 어르신의 {관계}"** 형태로만 쓴다
- 적용 대상: 추억 목록·상세의 생성자 표시(A3), 가족 구성원 확인 화면(A2)
- 어르신이 2명 이상이면 한 보호자가 어르신마다 다른 라벨을 갖는다. 이때는
  **현재 보고 있는 어르신 기준 라벨** 하나만 표시한다 (전부 나열하지 않는다)
- 다른 보호자의 라벨을 **내가 수정할 수 없다** — 이미 코드로 강제됨(`ChangeGuardianRoleUseCase`)

#### 요약

| 관계 | 표시 대상 | 상태 |
| --- | --- | --- |
| 보호자 → 어르신 | 내 링크의 라벨 (1인칭) | ✅ 구현 |
| 어르신 → 보호자 | 생성자 라벨 (`기타`·`보호자`는 생략) | ⚠️ 노출되나 규칙 미정 |
| 보호자 → 다른 보호자 | `{어르신}의 {관계}` 형태 | ❌ 경로 없음 (A2·A3 선행) |

| A12 | **관계 라벨 쓰기 경로가 2개** | `PATCH /elders/{id}/link/role`(단건)과 `PATCH /profile`의 `elderRoles` 맵(일괄)이 공존한다. 같은 "본인 링크 아님" 상황에 전자는 `NOT_RESOURCE_OWNER`, 후자는 `CARE_ACCESS_DENIED`를 던져 **에러 코드가 불일치**한다 | ✅ 종결 ([#31](https://github.com/memeboomemeboo/haemi-server-v2/issues/31)) |
| A13 | **`creatorRole`이 null이 될 수 있다** | `ElderMemoryQueryImpl.toItem()`이 링크를 조회해 관계를 붙이는데, **링크가 해제된 보호자**가 만든 추억은 `creatorRole=null`이 된다. `createdBy`가 null인 경우 `creatorName`도 null. 프론트는 두 값 모두 null 분기가 필요하다 | ✅ 종결 ([#32](https://github.com/memeboomemeboo/haemi-server-v2/issues/32)) — API 문서에 null 조건 명시, fallback 없음 |
| A14 | **참여 빈도 표시 단위가 명세와 충돌** | D7은 "주별·월별만, 일별 없음"으로 확정됐으나, 명세 RPT-ATT-003은 **"요일별 완료 점(●○)"** 즉 일별 표시를 규정한다. 컨디션 카드 시안도 일별이다(C2). 어느 쪽을 따를지 정해야 리포트 착수가 가능하다 — **D12: 일·주·월 모두 제공** | ✅ 종결 |
| A19 | **어르신 답변에 개수 제한도, 취소 경로도 없다** | `ResponseController`는 POST 4종(감정·텍스트·이미지·음성)만 있고 **DELETE·PATCH가 없다.** 같은 추억에 몇 번이든 답변이 쌓이고, 잘못 보낸 답변을 **어르신 본인도 보호자도 지울 수 없다.** 고령 사용자의 더블탭·오터치를 감안하면 중복 답변이 일상적으로 발생한다 — **D18: 취소·제한 모두 두지 않음** | ✅ 종결 |
| A20 | **어르신 답변 음성만 길이 검증이 빠져 있다** | 하루 한마디는 60초로 검증하는데(`DailyCareProperties`), `CreateResponseUseCase.voice()`는 `confirmUpload()`에 **기대 길이를 넘기지 않아** 미디어 정책 상한인 **180초까지 통과**한다. 어르신 답변 음성의 길이 규정 자체가 미확정 — **D20: 어르신 3분이 의도된 값** | ✅ 종결 |
| A21 | **추억 등록에 개수 제한이 없다** | 하루 한마디는 `(보호자, 어르신, 날짜)`당 1회로 막는데, 추억은 **하루 무제한**이다. 보호자 8명이 동시에 올리면 어르신 앨범이 감당 못 할 양으로 쌓인다. 두 기능의 제약이 비대칭인 이유가 명세에 없다 — **D19: 제한 없음 확정** | ✅ 종결 |
| A15 | **하루 한마디 보관 기간 안내 없음** | `retentionDays` 경과 시 어르신 인박스에서 사라지는데, 보호자는 언제 사라지는지 알 수 없다 — **D22: 구현 단계 아님, 보류** | ⏸ 보류 |

## 5. 프론트 화면 분기 규칙 (그대로 사용 가능)

| 화면 | 규칙 |
| --- | --- |
| 추억 상세 | 수정·삭제 버튼은 **내가 만든 추억에만** 노출. 남의 추억은 조회 전용 — **A3 해결 전까지 구현 불가** |
| 추억 목록 | 다른 보호자가 올린 것도 전부 표시 (합류 전 과거분 포함 — R4) |
| 하루 한마디 | 다른 보호자가 보낸 한마디는 **존재 자체를 표시하지 않는다.** 홈 완료 체크는 "내가 오늘 보냈는가"만 의미 |
| 어르신 카드 | 관계 라벨은 **보는 사람 기준**(1인칭). 같은 어르신도 보호자마다 다른 라벨 |
| 어르신 화면의 생성자 | `기타`·`보호자` 라벨이면 **관계 생략하고 이름만** 표시 (Q8-1). `creatorName`·`creatorRole`은 **null 가능** (A13) |
| 보호자 화면의 타 보호자 | 라벨 단독 사용 금지. **`{어르신 이름} 어르신의 {관계}`** 형태로만 표시 (Q8-1) |
| 어르신 컨디션 | **A4 해결 전까지 섹션 숨김 또는 스켈레톤.** 지금 실제 값이 나오는 건 어르신 선택 드롭다운뿐 (Q5-1) |
| 컨디션 점수 표기 | **수치 금지**(A16 확정 전). 3색 라벨 + "이번 주 N/7일" 게이지로 대체 |
| 참여 빈도 | **주별·월별만**. 일별 그래프 없음 (D7) |
| 리포트 | 보호자 전용. 어르신 화면에 진입 경로를 두지 않는다 (D5) |
| 마이페이지 링크 해제 | 마지막 보호자면 409 → "가족에 보호자가 최소 1명 남아야 합니다" 안내 |
| 어르신 프로필 수정 | 모든 링크된 보호자에게 동일하게 열어 둔다 (잠금 UI 불필요) |
| 보호자 프로필 | 본인 것만. 타인 프로필 진입 경로 없음 (D6) |
| 어르신 답변 버튼 | 전송 후 **버튼 비활성화·중복 전송 차단을 프론트에서** 처리해야 한다. 서버는 중복을 막지 않고 취소 API도 없다 (A19) |
| 가족 화면 | 사용자당 가족은 **항상 1개** — 목록 화면이라는 개념이 없다. 미소속이면 가족 생성 유도 (D10) |
| 가족 화면 분할 | `GET /families/my` **응답 1건을 프론트가 나눠서** 요약·구성원·어르신 영역으로 렌더링. 추가 API 호출 없음 (D10) |
